# Optimal Round

**178 classic coding problems across 22 topics — solved by hand, verified by a test runner.**

This is a practice repository. Every problem is a single self-contained file whose
header states the problem, its constraints, worked examples, edge cases, and the
time and space complexity a good solution must hit. The body is an empty stub.
You clone it, you fill the stubs in, and `./practice` tells you whether you were
right — and whether you were fast enough.

Clone it and start:

```bash
git clone https://github.com/sarmadkung/optimal-round
cd optimal-round
./practice list --todo
```

---

## No AI solved these problems

**Every solution in this repository is written by a human, by hand.** No AI
assistant, no autocomplete, no code generator, no copy-paste from a model. That is
the entire point of the repository: a solution you did not work out yourself
teaches you nothing, and a repository of generated answers measures nothing.

To be precise about what that pledge does and does not cover:

| | |
|---|---|
| **Solutions** — every filled-in stub | Written by hand. No AI. |
| Problem statements, constraints, complexity notes | Scaffolded with AI assistance, then reviewed |
| The `practice` test runner and test cases | Scaffolded with AI assistance |

The distinction matters. The scaffolding is infrastructure — a nicer way to state
a problem and check an answer. The **solving** is the work, and the work is mine.
The analytics below are only meaningful because of that.

## What's in here

Problems are grouped into 22 topic folders, ordered roughly from foundational to
advanced. Each folder is a pattern worth learning as a unit — the point is not to
memorise 178 answers, but to recognise which of about 20 shapes a new problem is.

| Browse | |
|---|---|
| [PROBLEMS.md](PROBLEMS.md) | Everything, grouped by topic, with solved status |
| [EASY.md](EASY.md) · [MEDIUM.md](MEDIUM.md) · [HARD.md](HARD.md) | Grouped by difficulty |
| [GUIDE.md](GUIDE.md) | How to read a problem and pick the right technique |
| [ai/](ai/README.md) | 30 AI problems in Python: ML, LLM internals, generative AI, RAG, agentic AI, reasoning. Graded offline with `ai/practice` |
| [algorithms/](algorithms/README.md) | 23 named algorithms explained in words, with practice problems |

A problem file looks like this:

```js
/**
 * 001 — Two Sum
 * Difficulty: Easy   ·   Topic: Arrays & Hashing
 * ----------------------------------------------------------------------
 * PROBLEM
 *   Given an array of integers `nums` and an integer `target`, return the
 *   indices of the two numbers such that they add up to `target`.
 *
 * CONSTRAINTS
 *   2 <= nums.length <= 10^5
 *
 * EXAMPLES
 *   twoSum([2, 7, 11, 15], 9)   ->  [0, 1]
 *
 * EDGE CASES
 *   - Duplicate values that form the answer ([3,3]).
 *
 * FOLLOW-UP
 *   - Can you come up with an algorithm that is less than O(n^2) time complexity?
 *
 * -------------------------- SPOILERS BELOW --------------------------
 *
 * HINTS
 *   1. ...
 *
 * COMPLEXITY
 *   Naive:  O(n^2) time — test every pair with nested loops.
 *   Target: O(n) time, O(n) space — one pass with a hash map.
 * ----------------------------------------------------------------------
 */

function twoSum(nums, target) {
  // TODO: your solution here
}

module.exports = { twoSum };
```

**Everything above the spoiler bar is what a platform would show you**, and it is
deliberately all you get: the statement, the constraints, worked examples, the
input edge cases you have to survive, and the platform's own follow-up question.
Deciding *which* complexity is achievable is half the exercise, so the target is
not stated up front.

**Below the bar are the answers** — the approach hints, and the naive and target
complexities. Read them when you are stuck, or afterwards to check you aimed at
the right solution. The perf case still enforces the target either way, so you
find out whether you hit it without having to look.

Some problems carry two extra sections above the bar:

- **INPUT FORMAT** — on tree, linked-list and graph problems, spelling out that
  your function receives a real node object and that the array in the examples is
  only how the platforms *print* it.
- **API** — on design problems (`LRUCache`, `MinStack`, `Trie`, …), the exact
  method signatures, return types and return contracts, as a platform specifies
  them.

## How to practice

Pick a problem, open the file, replace the `// TODO` with your solution. Two
sensible routes through the set:

- **By difficulty** — work [EASY.md](EASY.md), then [MEDIUM.md](MEDIUM.md), then
  [HARD.md](HARD.md). Best for building general fluency.
- **By topic** — pick a folder and go top to bottom; problems are ordered by
  difficulty within each one. Best for drilling a specific weakness.

Or let the tool choose — `./practice stats` ends with a suggested next problem,
preferring topics you have already started.

## Checking your work

```bash
./practice c 001        # one problem
./practice c 01         # a whole topic folder
./practice c            # everything you have attempted
./practice stats        # analytics, difficulty and topic breakdown
./practice list --todo  # what you have not started
```

```
  001  Two Sum   Easy · Arrays & Hashing

    ✓  twoSum([2,7,11,15], 9)  →  [0,1]
    ✓  twoSum([3,2,4], 6)  →  [1,2]
    ✓  twoSum([3,3], 6)  →  [0,1]
    ✓  perf · 200k elements  →  13ms (budget 1000ms)

    PASS  4/4 cases · complexity target met
```

That last line is the one that matters. Problems carry a **perf case** on a
large input with a time budget, because correctness alone will not tell you
whether you wrote the solution the header asked for — the naive version passes
all the small examples too. Write Two Sum with nested loops and you get this:

```
    ✓  twoSum([2,7,11,15], 9)  →  [0,1]     ← every example still passes
    ✗  perf · 200k elements  →  KILLED after 4000ms (budget 1000ms)
         Too slow for the input size — check the Target line in the file header.

    FAIL  4/4 cases · complexity target MISSED
```

The perf case runs in a separate process and is killed at three times its budget,
so a slow solution reports a failure instead of hanging your terminal.

Perf cases measure **time only**. They catch a solution in the wrong complexity class
(quadratic where linear was asked for), but not one that is fast and uses too much
memory — so where the naive approach differs only in space (a hash map instead of
Boyer-Moore voting, say), the header's Target line is on your honour. Perf cases
currently cover Arrays & Hashing and Two Pointers; the other topics check
correctness only.

`./practice` exits non-zero on failure, so CI can run it.

## Layout

```
practice              the test runner and analytics tool
problems/             178 problems in 22 topic folders
problems/_lib/        TreeNode and ListNode, and the array <-> node serializers
algorithms/           23 named algorithms explained in words, each linked to practice problems
GUIDE.md              how to read a problem and choose a technique
tests/                test cases as JSON data, plus the large-input perf cases
PROBLEMS.md           full index by topic          (generated)
EASY|MEDIUM|HARD.md   indexes by difficulty        (generated)
```

Test cases are stored as plain **data**, not code:

```json
{
  "fn": "twoSum",
  "cases": [
    { "in": [[2, 7, 11, 15], 9], "out": [0, 1] },
    { "in": [[3, 2, 4], 6], "out": [1, 2] }
  ]
}
```

That is deliberate. The same JSON can drive a Go, Python or Rust runner later
without a single test case being rewritten.

Tree and linked-list problems declare the node shape, and the runner builds real
nodes from the arrays before calling you — the same translation the platforms do:

```json
{
  "fn": "maxDepth",
  "inTypes": ["tree"],
  "cases": [{ "in": [[3, 9, 20, null, null, 15, 7]], "out": 3 }]
}
```

```json
{
  "fn": "reverseList",
  "inTypes": ["list"],
  "outType": "list",
  "cases": [{ "in": [[1, 2, 3]], "out": [3, 2, 1] }]
}
```

`inTypes` names the shape of each argument and `outType` the shape of the return
value. The types are `tree` (level-order array, `null` for a missing child),
`list` (values in order), `cycleList` (`[values, pos]`, where `pos` is the index
the tail points back to, or -1), and `node` (a single node, compared by its
`val`). Anything else is passed through as plain JSON.
